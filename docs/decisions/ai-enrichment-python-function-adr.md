# ADR: Introduce a Python‑Based AI Photo Enrichment Service (Separate from CloudCanvas Backend)

## Status

Accepted

## Context

CloudCanvas is a .NET/Angular application with a clean architecture, using Cosmos DB as the main store for photo projections and Azure Blob Storage for images. The next major feature is AI‑driven photo enrichment: automatic tags and captions generated by Azure AI Vision and written back into the existing photo documents via PATCH.

There are two overlapping goals:

- Build a **real, portfolio‑worthy feature** for CloudCanvas (AI tags/captions on photos).
- Use the implementation as a **learning vehicle for AI‑200**, which leans heavily on Python and Azure AI SDK usage.

The core questions were:

1. **Where should the enrichment logic live?**
   - Inside the existing CloudCanvas .NET backend?
   - In Azure Functions (C\# or Python) tied directly to events?
   - In a separate backend service?
2. **How should AI metadata be stored?**
   - In the same Cosmos DB container as the photo documents?
   - In a separate container or store for AI‑specific fields?

## Decision

Introduce a **minimal Python backend service** (“AI Photo Enrichment Service”) that:

- Exposes a small HTTP API for enrichment in early phases (and later also runs as event‑driven Azure Functions).
- Uses **Python** (with FastAPI or similar) as the primary implementation language for AI calling logic.
- Shares the **same Cosmos DB container** as CloudCanvas for photo documents, using PATCH to add AI metadata fields (`ai-tags`, `ai-caption`, etc.) to the existing projection.

This service is intentionally small and focused: one domain (photo enrichment), one main responsibility (call Azure AI Vision and update Cosmos), and tightly aligned with AI‑200 learning objectives.

## Options Considered

### Option 1 – Implement enrichment directly inside the existing .NET CloudCanvas backend

**Description**
Extend the CloudCanvas ASP.NET Core backend with:

- New endpoints or background handlers that:
  - Call Azure AI Vision/Image Analysis using the .NET SDK.
  - Update the photo documents in Cosmos DB with AI metadata.

**Pros**

- Single technology stack (.NET/C\#) and codebase.
- Reuses existing architecture, DI, logging, and deployment pipeline.
- Easier integration with existing domain boundaries and application services.

**Cons**

- Does not leverage Python, which is central to most AI‑200 labs and examples and is often closer to the “first‑class” Azure AI SDK experience.
- Less opportunity to demonstrate **polyglot, multi‑service architecture** around a single domain (which is attractive for portfolio and interviews).
- Tighter coupling between AI logic and CloudCanvas backend; harder to iterate independently or swap AI models/services over time.

**Outcome**
Rejected as the primary path for enrichment because it keeps everything inside the .NET bubble and misses the chance to:

- Practice Python and its Azure AI SDKs.
- Show a clean, language‑agnostic architecture where AI logic lives in its own service.

***

### Option 2 – Use Azure Functions (C\# or Python) directly against Blob events (no separate service)

**Description**
Implement the entire enrichment pipeline as Azure Functions:

- Blob trigger (C\# or Python) when a photo or thumbnail is uploaded.
- Function calls Azure AI Vision and updates Cosmos DB.

**Pros**

- Classic serverless pattern: upload → trigger → process → write back.
- No dedicated “backend service” – just Functions connected to storage, AI, and database.
- Fits many Azure reference architectures for image processing.

**Cons**

- If used **instead of** a dedicated Python service, it makes the AI logic harder to treat as a self‑contained backend that can be tested or extended outside the event pipeline.
- Coupling is driven by storage events; CloudCanvas has less explicit control over when enrichment happens unless more orchestration is added (Service Bus, flags, etc.).
- For AI‑200 learning, having a small, testable Python API (plus Functions around it) gives clearer separation of concerns than “everything in Functions from day one.”

**Outcome**
Functions **are still part of the plan**, but not as the only place where enrichment logic lives. Instead, the decision is to:

- Put core enrichment logic in a Python module/service (HTTP‑callable).
- Wrap that logic in Azure Functions triggers (HTTP, Service Bus, or Cosmos change feed) as the next step.

***

### Option 3 – Separate store for AI metadata (new container or table)

**Description**
Create a separate Cosmos DB container (or other data store) dedicated to AI metadata:

- Photo documents in the “main” container.
- AI tags/captions in an “AI metadata” container keyed by photo ID.

**Pros**

- Clear technical separation between core photo metadata and AI‑generated fields.
- Potentially different lifecycle, retention, or access policies for AI data.

**Cons**

- Cosmos DB does not support joins across containers; client‑side orchestration is required to combine photo + AI data.
- For this feature, AI tags/captions are conceptually part of the **photo projection**; scattering them across containers introduces complexity with limited benefit.
- Shared partition key and frequent joint access argue for keeping related data together in a single container.

**Outcome**
Rejected for this feature. AI metadata will be stored on the **same photo document** in the existing container, added via PATCH operations. This keeps a single source of truth for each photo and avoids cross‑container querying.

***

## Rationale for the Chosen Approach

1. **Python aligns with AI‑200 and Azure AI SDK evolution**
   - Microsoft guidance and ecosystem trends emphasize Python for AI experimentation and SDK support, especially for newer Azure AI and OpenAI features.
   - Building a dedicated Python service lets this feature double as an AI‑200 learning vehicle: Python code, Azure Functions, bindings, and AI Vision usage.
2. **Polyglot architecture is a portfolio asset**
   - CloudCanvas remains a .NET/Angular app, but AI enrichment is handled by a separate Python service.
   - This demonstrates comfort with multi‑language, multi‑service architectures on Azure, which is valuable for interviews and real‑world systems.
3. **Shared Cosmos DB container keeps the domain coherent**
   - Photo documents and their AI tags/captions belong together conceptually and are frequently accessed together.
   - Using the same container with a PATCH‑based approach avoids cross‑container joins and keeps the photo projection as the single source of truth.
4. **Separation of concerns between orchestration and intelligence**
   - CloudCanvas continues to own user‑facing workflows and core domain logic.
   - The Python AI service owns “intelligence”: calling Azure AI Vision, shaping AI outputs, and writing them back to Cosmos.
   - Azure Functions triggers (HTTP, Service Bus, change feed) orchestrate **when** the AI logic runs, without embedding it inside CloudCanvas directly.

## Consequences

- CloudCanvas remains clean and focused as a .NET application; AI logic does not clutter its backend.
- A separate Python service plus Functions provides a strong platform for AI‑200 preparation and experimentation with Azure AI Vision, Cosmos DB bindings, and serverless patterns.
- Operationally, there is now an additional service/codebase to maintain, but it is small and deliberately scoped.
- Future ADRs (like the trigger‑selection ADR) can focus purely on how this Python enrichment service is invoked (HTTP, Service Bus, Cosmos change feed) without revisiting the language or data‑model choice.
